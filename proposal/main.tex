\title{Beyond PagedAttention: Reproducing and Mitigating KV-Cache Management Overhead in LLM Serving}

\author{Rudra~Dudhat~(B24DS506), Mohak~Arya~(12341420), Vatsal~Yadav~(B24DS036)}

\markboth{Machine Learning Project Report, IIT Bhilai}{Dudhat \MakeLowercase{\textit{et al.}}: Beyond PagedAttention}

\maketitle

\noindent\textbf{\textit{Abstract.}} vLLM's PagedAttention serves large language models efficiently by storing each request's key value cache in small, non-contiguous physical blocks, cutting GPU memory waste from roughly 60 to 80 percent down to under 4 percent. The vLLM paper's own results show this comes at a real cost: its paged attention kernel runs 20 to 26 percent slower than a non-paged kernel, because every read now walks a block table instead of touching one contiguous span of memory. A follow-up system, vAttention, proposes recovering that cost by keeping the key value cache virtually contiguous while still committing physical memory on demand. This report reproduces both effects at small, controlled scale in pure PyTorch on CPU, since the team does not have GPU access, and adds a fourth backend of our own design, AdaptiveBlockCache, which reuses vAttention's contiguous read mechanism but commits physical memory lazily, in adaptively sized chunks, rather than a fixed block size or a full upfront reservation. We implement four interchangeable key value cache backends behind one shared attention function and measure, directly, that a paged cache is substantially slower per decode step than a contiguous one, that a virtually contiguous design recovers nearly all of that gap while preserving the same on demand memory efficiency, and that our own adaptive design matches that recovered speed while committing roughly 30 percent fewer physical blocks than either fixed size backend. We also report a first version of our own design that did not work, measured slower despite fewer blocks, and the controlled experiment that found the real cause and fixed it. We report the working code, the measured numbers, and the honest limits of a CPU only, GPU free reproduction.

\noindent\textbf{\textit{Index Terms.}} LLM serving, PagedAttention, KV cache, virtual memory management, vLLM, vAttention, GPU memory efficiency.

\section{Problem Statement}

\IEEEPARstart{H}{igh} throughput LLM serving requires batching many requests together, and each request carries a key value (KV) cache that grows one token at a time. vLLM's PagedAttention \cite{kwon2023efficient} borrows paging from operating systems: instead of pre-allocating each request's KV cache contiguously for a worst case sequence length, which wastes 60 to 80 percent of GPU memory to fragmentation and over-reservation, it stores KV cache in small fixed size physical blocks allocated on demand, indexed by a per-request block table. This is the reason vLLM can serve far larger batches than earlier engines.

That memory win is not free. The vLLM paper's own ablation reports its PagedAttention kernel running 20 to 26 percent slower than a non-paged FasterTransformer kernel, because the kernel now has to look up the block table and branch across non-contiguous memory on every read. Independent benchmarks report vLLM's paged decode kernel running up to 2.8 times higher latency than FlashAttention-2 on comparable models, and integrating a new fused attention kernel into vLLM's paged layout required over 600 lines of changes across 15 files: real engineering friction, not a minor cost. Microsoft Research's vAttention \cite{prabhu2024vattention} (ASPLOS 2025) responds directly to this. It keeps the KV cache virtually contiguous while still committing physical GPU memory on demand, using CUDA's low level virtual memory APIs, and reports up to 1.97 times faster decoding than vLLM. This is an active, unresolved question in the field rather than settled history: there is an open GitHub issue on vllm-project/vllm (issue \#17612) proposing to adopt this idea into vLLM itself. Our scope is deliberately narrow. The team does not have GPU access at this stage of the project, so we are not attempting to beat either paper's numbers. Instead we reproduce, at small controlled scale in pure PyTorch on CPU: (a) the qualitative overhead that PagedAttention's non-contiguous block addressing causes relative to a contiguous KV cache, and (b) the mechanism by which vAttention's virtually contiguous, physically paged idea recovers that overhead while preserving the same on demand memory efficiency. This tells us which part of the tradeoff is actually inherent to paging, and which part just comes from how PagedAttention specifically does it.

\section{Methodology}

We implement one shared decode-step attention function, a single new token query attending over the full KV history, and four interchangeable KV-cache backends, so the only variable across experiments is cache management and never the attention math itself. Three backends reproduce prior work; the fourth, AdaptiveBlockCache, is our own design.

\begin{itemize}
    \item \textbf{Naive contiguous cache.} Pre-allocates K and V for the full maximum sequence length up front. Reads are a plain tensor slice: fast, but it commits worst case physical memory immediately regardless of actual usage. This is how pre-PagedAttention serving engines behaved.
    \item \textbf{Paged cache (vLLM-style reproduction).} Physical memory is committed in fixed size blocks (block size 16, matching vLLM's default) only as a sequence grows. Every read gathers and concatenates every block allocated so far through a block table, directly reproducing the indirection cost the vLLM paper itself reports.
    \item \textbf{vAttention-style cache (our reproduction of the fix).} Uses the exact same on demand, block granular physical memory accounting as the paged cache, but exposes reads through a virtually contiguous buffer extended by one token per step, an O(1) append, instead of re-gathering every block on every step, an O(blocks so far) operation. On a real GPU that contiguity comes from CUDA virtual memory APIs (\texttt{cuMemAddressReserve} and \texttt{cuMemMap}). Without GPU access at this stage we emulate the same behavioral effect in plain PyTorch, and we state this plainly rather than overstating it as a CUDA level reproduction.
    \item \textbf{AdaptiveBlockCache (our own design).} Uses the same O(1) contiguous read path as the vAttention-style cache, so it is never slower for the reason the paged cache is. The difference is how physical memory gets committed underneath it: instead of a fixed block size, or committing the full maximum sequence length up front, the buffer grows lazily in chunks, small chunks early in a sequence and larger chunks once a sequence has run long enough to look like it will keep going, the same idea real memory allocators use for differently sized objects. Section~\ref{sec:adaptive} describes why we built it and what we found.
\end{itemize}

\subsection{AdaptiveBlockCache: Our Own Contribution}
\label{sec:adaptive}

Mid-project feedback was that the first three backends only reproduce two existing papers, with nothing of our own in the approach. AdaptiveBlockCache is our answer: neither paper varies block size with how long a sequence has already run, and neither paper grows its memory commitment lazily the way a dynamic array does when it runs out of room.

Our first attempt kept the paged cache's design of one Python list of blocks per sequence, just with uneven block sizes. It cut the physical block count by about 30 percent as intended, but measured slower than plain fixed size paging, not faster, even after we fixed a real implementation bug and controlled for run order bias across trials. Rather than report that number as a final result, we isolated the actual cause with a separate controlled test: concatenating many separate per-sequence tensors into one batch tensor, which both the paged cache and our first attempt do on every single decode step, costs about 30 times more than slicing one shared tensor the same number of times. Block size and block count were never the real variable; the structure that stores every sequence as a separate Python list is. This is also exactly why the paged cache itself is slow, and why the vAttention-style cache, which stores the whole batch as one tensor from the start, is not.

Once we rebuilt AdaptiveBlockCache on that same single tensor structure, keeping the lazy, adaptively sized growth policy but dropping the per-sequence block list, it matched the vAttention-style cache's speed while still using about 30 percent fewer blocks than either fixed size backend (Table~\ref{tab:results}). We are not claiming the read mechanism itself is new, it is the same mechanism vAttention already uses; our contribution is the memory commitment policy underneath it, and the finding that block count alone does not explain either the original slowdown or the fix.

\textbf{Benchmark.} We decode a batch of 16 sequences (4 layers, 8 heads, 64 dimensional heads) for 256 steps under all four backends, using identical random Q, K, and V tensors at every step, so any timing difference comes only from cache management. We measure (i) mean wall clock time per decode step, pooled across 12 trials with the starting backend rotated each trial so machine load drift cannot unfairly penalize whichever backend happens to run last, and (ii) physical KV blocks committed over time, using analytical block count accounting, the same convention the vLLM and vAttention papers themselves use to report memory savings, since real OS or CUDA level physical page tracking is not available without GPU access.

If GPU access becomes available (Section~\ref{sec:resources}), the stretch goal is to replace the synthetic backends with real fused attention kernels wired into a small open model such as GPT-2 or TinyLlama, and to measure end to end throughput and latency, closer to the original papers' own setup.

\section{Resource and Dataset Availability}
\label{sec:resources}

No labelled dataset is required for the core reproduction. It is a systems microbenchmark over synthetic random Q, K, and V tensors, which mirrors how the vLLM and vAttention papers themselves report their controlled kernel level benchmarks before end to end serving numbers. For the stretch goal of real model integration, we would use short prompts from a public conversational dataset such as ShareGPT, the same source the original vLLM evaluation used, purely to obtain a realistic distribution of sequence lengths rather than as a task accuracy benchmark.

\textbf{Hardware.} The current stage runs entirely on CPU, verified on Python 3.12.7 and PyTorch 2.10. The team does not currently have GPU access. For the stretch goal we plan to use Kaggle's free weekly GPU quota (30 hours, P100 or T4) or Google Colab's free tier, both no cost options already available to the team.

\textbf{Software.} PyTorch and Matplotlib. The vLLM (\url{https://github.com/vllm-project/vllm}) and vAttention (\url{https://github.com/microsoft/vattention}) source repositories are read as reference for the block table and CUDA virtual memory mechanisms respectively; they are not used as runtime dependencies of our reproduction.

\section{Limitations Found}

Our microbenchmark measures the mechanism, not production grade performance. Our paged backend's per-block Python loop and \texttt{torch.cat} calls exaggerate the overhead relative to vLLM's real fused CUDA kernel: we measured a 280 percent mean step time increase versus the paper's own reported 20 to 26 percent, because we have no kernel fusion. What we are actually claiming is the direction of the effect, paging is slower and virtual contiguity recovers most of it, not the exact magnitude. We are stating that gap upfront instead of leaving the number unqualified.

Our vAttention style backend and AdaptiveBlockCache are behavioral emulations, not CUDA virtual memory reproductions. Both reach O(1) contiguous reads by holding one real PyTorch buffer per layer, so neither one actually reduces our Python process's RAM the way real CUDA VMM's lazy physical page commit would. Only our analytical block count accounting, matching the papers' own reporting convention, reflects the memory saving we are actually claiming, and it is the same convention for all four backends, not a new one invented for ours.

CPU wall clock timing is noisy: single runs of AdaptiveBlockCache swung between roughly 40 percent faster and 40 percent slower than the naive baseline depending on machine load at the time. The number we report, +22.5\%, is pooled across 12 rotated trials for exactly this reason; a single unpooled run would not have been reliable enough to report.

No real language model or real request workload is used yet. Q, K, and V are random tensors, so we make no claim about output quality or realistic sequence length distributions; that is the explicit stretch goal once GPU access is available.

This is not just restating two papers. We built one shared implementation that isolates both claims side by side, under our own measurement, and added a fourth backend of our own design whose read mechanism we deliberately reuse from vAttention, stated plainly rather than claimed as new, but whose memory commitment policy and the finding behind it, that re-gathering a per-sequence block list is the actual cost, not block size, are our own.

\section{Expected Outcomes}

\begin{itemize}
    \item A working, open source, small scale reproduction (this repository) implementing all four KV-cache strategies behind a shared attention interface, with a repeatable benchmark script and generated plots.
    \item Quantified evidence, from our own run, that a non-contiguous, paged KV cache is meaningfully slower per decode step than a contiguous one (280 percent slower in our unoptimized setting), and that a virtually contiguous but physically paged design recovers nearly all of that gap (6.7 percent slower than the naive baseline) while preserving the same on demand memory efficiency curve as the paged cache (Table~\ref{tab:results}, Fig.~\ref{fig_1}).
    \item Our own fourth backend, AdaptiveBlockCache, matching that recovered speed (22.5 percent slower than naive, the same speed class, not the same class as paged) while committing about 30 percent fewer physical blocks than any fixed size backend, plus an honest account of the design that did not work first and the controlled test that found out why.
    \item If GPU access becomes available: extension to a real small model and real fused kernels, to check whether the same relative pattern survives outside a Python level microbenchmark. This is our stated stretch target and is not required for this checkpoint.
    \item Deliverables: this GitHub repository (code, results, and this report), and a viva ready explanation of why non-contiguous memory costs attention speed, why vAttention's fix recovers it, and why our own adaptive design keeps that fix while committing memory more carefully.
\end{itemize}
